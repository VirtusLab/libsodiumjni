Short reference for AI agents. For task-specific guidance, load the skills from
**[agent-skills/](agent-skills/)** when relevant.

> **LLM Policy**: All AI-assisted contributions must comply with the
> [Scala CLI LLM usage policy](https://github.com/VirtusLab/scala-cli/blob/main/LLM_POLICY.md). The contributor
> (human) is responsible for every line. State LLM usage in the PR description.

## Purpose: a dependency of Scala CLI

libsodiumjni is a minimal set of JNI bindings for [libsodium](https://github.com/jedisct1/libsodium), meant
**primarily to be used by [Scala CLI](https://github.com/VirtusLab/scala-cli)** (to encrypt GitHub secrets, in
`github secret create` / `publish setup`). It uses JNI rather than JNA because JNI works in GraalVM native images.

**Compatibility with Scala CLI is always a requirement.** Any change that breaks something Scala CLI relies on must be
avoided, or, if unavoidable, stated clearly as a breaking change in the commit message and the PR description, with what
Scala CLI needs to change. Check Scala CLI's usage (`LibSodiumJni.scala`, `LibsodiumjniFeature.java`,
`copyLibsodiumjniTo` in its build, `GitHubTests.scala`) before changing any of these:

- Maven coordinates: `org.virtuslab.scala-cli:libsodiumjni`
- Java API: `libsodiumjni.Sodium` (`init`, `keyPair`, `seal`, `sealOpen`), `libsodiumjni.KeyPair`, and
  `libsodiumjni.internal.LoadLibrary` (`initialize(path)` in Scala CLI, `initializeFromResources()` in its tests).
  `LoadLibrary` is used by Scala CLI despite its `internal` package. `SodiumApi` isn't used directly.
- Per-platform artifacts: `libsodiumjni-<version>-<classifier>.<ext>`, with classifiers `<arch>-<os>` like
  `x86_64-pc-linux`, `aarch64-apple-darwin`, `x86_64-pc-win32` (the ones Scala CLI computes, see
  `FetchExternalBinary.platformSuffix` there), shared (`so` / `dylib` / `dll`) and static (`a` / `lib`) libraries.
- GraalVM native image static linking: Scala CLI registers the built-in library `sodiumjni` and the JNI package prefix
  `libsodiumjni_`, so the native library names and the JNI symbol names (`Java_libsodiumjni_internal_SodiumApi_*`, i.e.
  the `libsodiumjni.internal.SodiumApi` class name and package) are part of the contract. The static libraries only
  contain the libsodiumjni code: Scala CLI links libsodium itself after them.
- The native libraries bundled in the JAR, under `META-INF/native/<dir>/` (see `LoadLibrary.resourcePath`).

## Repository layout

Single Mill module, `libsodiumjni` (Java + C), with its tests in `libsodiumjni.test` (JUnit 4).

| Path                                                       | Contents                                                                                 |

| `libsodiumjni/src/main/java/libsodiumjni/`                 | Public API (`Sodium`, `KeyPair`, `SodiumException`)                                      |

## Build and test

[Mill](https://mill-build.org/), launchers in the repo (`./mill`). JDK 17.

```bash
./mill -i __.compile                                               # compile Java, generate the JNI header, build the native library
./mill -i __.test                                                  # all tests
./mill -i libsodiumjni.test.testOnly libsodiumjni.tests.SodiumTests  # one test class
./mill -i libsodiumjni.test.testOnly libsodiumjni.tests.SodiumTests -- '--tests=sealAndOpenRoundTrip'  # one test
```

Native libraries are built for the build machine only (OS and CPU, from the `os.arch` of the JVM running Mill). The
CI builds each platform on its own runner, and the release job merges them. libsodium is built from source and linked
statically on Linux / macOS, and comes from its official MSVC build on Windows (linked dynamically). See
[agent-skills/](agent-skills/) to test on Linux from macOS, and for what can't be tested locally.

## Rules

- **Every change of logic needs automated tests**, written first when possible (check they fail before the change).
  Re-run the full test suite locally before submitting. Platform-specific tests use JUnit `Assume` to skip elsewhere.
- **Native code** (`libsodiumjni_internal_SodiumApi.c`): check arrays for null and every length before any memory access,
  copy array contents with `Get/SetByteArrayRegion`, wipe copied secrets with `sodium_memzero`, and keep it free of
  warnings (`-Wextra -Werror` on Linux / macOS). The public `Sodium` methods validate their arguments too, and throw
  `IllegalArgumentException` / `NullPointerException` for invalid ones, `SodiumException` for libsodium failures.
- **Commit the regenerated JNI header** along with native method changes: the CI fails if the build modifies tracked
  files.
- **Mill evaluates every task referenced in a `Task { … }` body, whichever `if` branch runs.** For OS- or
  architecture-specific tasks (which fail elsewhere), put the `if` outside, choosing between tasks
  (`def t = if Properties.isMac then Task { … } else Task { … }`).
- **No runtime dependencies**: the published POM must have none (JNA in particular).
- Build files follow `.scalafmt.conf` (100 columns).
- Don't claim something was tested on a platform it wasn't run on: state what was checked locally, and what's left
  to the CI (typically Windows).

## Releases

Releases are published to Maven Central by the CI, from `vX.Y.Z` git tags. Other commits get a `-SNAPSHOT` version, and
without git tags, the version is `0.0.0-SNAPSHOT` and publishing refuses to run (fetch tags with `git fetch --tags`).
